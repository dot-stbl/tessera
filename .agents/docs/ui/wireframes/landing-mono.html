Tessera is an observability UI for OpenTelemetry traces, logs and metrics that runs on the stack you already have. Correlation is deterministic — matched on trace_id / span_id, not guessed from timestamps. No ingest, no telemetry storage, no data-source plumbing.

02

Six decisions

what makes it different

Tessera is small on purpose. Each of these is a constraint we refuse to trade away, because together they are the reason the correlation works everywhere and the config survives a code review.

01

Deterministic correlation

Logs join spans on trace_id and span_id from the OTel log data model. No time-window heuristics, no "probably related". Either the id is there or the panel says so.

02

OpenTelemetry only

One canonical domain model — spans with span.kind, status.code, exception.* events; logs with severityNumber. Providers map their wire format into it. Nothing else is supported, and that is the feature.

03

Logic above the provider

Error detection, grouping, log linking and dependency extraction are written once, on the OTel model. A new backend is a new provider class — modules do not change. Enforced by architecture tests, not by convention.

04

Dependencies from spans

The service graph is derived from the traces themselves — CLIENT→SERVER across service.name, PRODUCER→CONSUMER via links, external nodes from peer.service / db.system. No backend dependency API required.

05

Everything as code

Dashboards are typed YAML with a JSON Schema, validated in CI, reviewed in a PR. You declare a row of three panels; a compiler does the layout. Nobody hand-writes grid coordinates.

06

Thin by contract

No ingest, no telemetry persistence, no query rewriting behind your back. The backend proxies to standard APIs and keeps your token server-side; browser state stays in the browser.

03

Architecture

references point downward only

Four layers, one rule: nothing points sideways or up. Modules know provider interfaces, never a vendor. Swapping the data source touches exactly one project.

layersnetarchtest-enforced
adding a backendroadmap
// 1 · implement the interfaces the modules already consume
internal sealed class TempoTraceProvider : ITraceProvider
{
    public Task<Trace> GetTraceAsync(TraceId id, CancellationToken ct);
    public Task<IReadOnlyList<TraceSummary>> SearchAsync(TraceQuery q, CancellationToken ct);
}

// 2 · map the wire format into the OTel domain — once
internal static Span ToDomain(this TempoSpan wire) => new()
{
    TraceId   = wire.TraceId,
    SpanId    = wire.SpanId,
    Kind      = wire.Kind.ToSpanKind(),
    Status    = wire.Status.ToStatusCode(),
    StartUnixMs = wire.StartUnixNano / 1_000_000,   // utc unix ms on the wire
};

// 3 · register it in the composition root
builder.Services.AddTempoProvider(config);

// modules: unchanged. tests: unchanged. ui: unchanged.
04

Dashboards as code

next milestone

Author format is not storage format. You write intent — a row of three panels, a query, a threshold — and the compiler resolves layout. It lives in git, it is validated in CI, and the validator's errors teach instead of just rejecting.

dashboards/checkout.yamljson-schema validated
apiVersion: tessera/v1
kind: Dashboard
metadata:
  name: checkout
  title: Checkout · RED
spec:
  variables:
    - name: service
      from: services          # discovered from spans
      default: checkout-api
  rows:
    - title: Golden signals
      panels:                  # layout is computed, not authored
        - stat:   rate
          query:  sum(rate(http_requests_total{service="$service"}[5m]))
        - stat:   errors
          query:  sum(rate(http_requests_total{service="$service",status=~"5.."}[5m]))
          thresholds: [{ gt: 0.01, level: warn }]
        - stat:   p95
          query:  histogram_quantile(0.95, sum by (le) (rate(...)))
    - title: Slowest operations
      panels:
        - table:  traces
          source: traces
          filter: { service: $service, minDuration: 500ms }

Why the error message matters. The validator is the interface an agent programs against. Errors that enumerate valid values and suggest the nearest one turn generate → validate → fix into a loop that converges without a human in it.

07

Where it actually is

no vapour

Tessera is pre-1.0 and this page does not pretend otherwise. The backend is done and tested; the UI is being wired to it now. Everything marked next is designed, not shipped.

MilestoneStatusWhat it covers
mvp-01 · backend shipped Traces, Logs, Discovery, Health modules · Victoria provider (Jaeger/LogsQL/PromQL) · span-tree reconstruction · ProblemDetails · resilience pipeline. 119/119 tests, 0 warnings.
mvp-02 · platform shipped TOML config + env routing · filesystem layout (Linux + Windows) · auth providers (guest, admin-bearer, LDAP, Keycloak) · EF Core/SQLite preferences · OTel self-telemetry · SPA bundled into the host image.
mvp-02 · console in progress The loop above, on live data: generated API client, trace explorer, waterfall, per-span logs, service inventory. Design system exists (~110 primitives, Ladle catalog); screens are being wired off mocks.
metrics + as-code next PromQL panels, dashboards as typed YAML, schema + validator with teaching errors, apply --dry-run, render preview.
second provider next Jaeger / Tempo / Loki behind the same interfaces — the claim in §03 gets its proof when the module code does not move.
alerting last Deliberately last. Alertmanager and friends already do this well; a half-built alert engine is worse than none.
Not planned: ingest, telemetry storage, anomaly detection, RUM, synthetic monitoring, cost attribution. Tessera reads what your stack already holds — that boundary is what keeps it thin enough to be trustworthy.
