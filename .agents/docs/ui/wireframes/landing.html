  1. 14:20:03alert fires

    Narrow to the failing requests

    Filter by service, status and duration. Error traces and latency outliers come first, so you are reading the request that broke instead of a sample of healthy ones.

  2. +8strace open

    Read the waterfall

    The span tree is rebuilt on the server from flat spans, so nesting and timing hold up. The span that owns the latency is visible before you read a single attribute.

  3. +19sspan selected

    Read that span's logs

    Selecting the span loads the log lines that carry its span_id. The retry, the timeout and the rollback, in order, without a second query to write.

  4. +27scause named

    Hand the link to someone else

    The trace id, the selected span and the time range live in the URL, so the link you paste into the incident channel opens on exactly what you were looking at.

Correlation

An id, not a time window.

OpenTelemetry already writes trace_id and span_id onto every log record emitted inside a span. Tessera reads exactly that field. There is no matching window to tune and no clock skew to correct for.

per trace
Every log carrying the trace id, in time order
per span
Narrowed to one span id, which is what the panel above shows
errors
Keyed off status.code, with exception.* events pulled out
no id
Listed separately. A log without a span id is never folded in as if it had one
Providers

Nothing above the provider knows it is Victoria.

Modules consume four interfaces from the shared kernel, and each provider maps its own wire format into the OpenTelemetry domain model. Error detection, grouping, log linking and dependency extraction are written once, above that line.

Adding a backend means one new project. Architecture tests fail the build if a module ever reaches for a vendor directly.

reads
Standard APIs only — Jaeger query, LogsQL, PromQL
writes
Nothing. No ingest, no telemetry storage, no query rewriting
secrets
Provider tokens stay server-side; the browser never receives one
topology
Service dependencies derived from spans, not from a vendor endpoint

Dashboards you can review in a pull request.

You write what you want on screen — a row of three panels, a query, a threshold. Layout is computed, the schema validates in CI, and a failed check tells you which values are allowed.

dashboards/checkout.yaml schema validated
apiVersion: tessera/v1
kind: Dashboard
metadata:
  name: checkout
spec:
  variables:
    - name: service
      from: services        # discovered from spans
      default: checkout-api
  rows:
    - title: Golden signals
      panels:                # no grid coordinates
        - stat: rate
          query: sum(rate(http_requests_total[5m]))
        - stat: errors
          thresholds: [{ gt: 0.01, level: warn }]
        - stat: p95

Install

Point it at what you already run.

One container, one config file, one port. Endpoints and tokens are read server-side.

docker-compose.yml ships today
services:
  tessera:
    image: ghcr.io/dot-stbl/tessera:latest
    ports: ["1990:1990"]
    volumes:
      - ./tessera.toml:/etc/tessera/tessera.toml:ro
      - tessera-data:/var/lib/tessera
    environment:
      TESSERA__ADMIN__TOKEN: ${TESSERA_ADMIN_TOKEN}

# the full stack — three victoria containers plus
# an otel collector — lives in /compose
/etc/tessera/tessera.toml ships today
[server]
port = 1990

[providers.victoria]
traces  = "http://victoriatraces:10428"
logs    = "http://victorialogs:9428"
metrics = "http://victoriametrics:8428"
# token = { env = "VICTORIA_TOKEN" } — never inline a secret

[auth]
provider = "guest"  # guest · admin-bearer · ldap · keycloak

[storage]
# sqlite, ui preferences only — no telemetry lands here
path = "/var/lib/tessera/tessera.db"
Status

What works today.

Tessera is pre-1.0. The backend is finished and tested; the console is being wired to it. Anything below marked designed is on this page as a plan, not a feature.

Backend Ships today

Traces, logs, discovery and health · Victoria provider over Jaeger query, LogsQL and PromQL · server-side span-tree reconstruction · typed errors as ProblemDetails · retry and timeout policies. 119 unit tests, no build warnings.

Platform Ships today

TOML config with environment overrides · filesystem layout for Linux and Windows · four auth providers, including LDAP and Keycloak · SQLite for UI preferences · OpenTelemetry self-telemetry · the SPA bundled into the host image.

Console Being wired

The four moves above, against live data: generated API client, trace explorer, waterfall, per-span logs, service inventory. The design system exists — around 110 primitives and a component catalogue; screens are moving off mock data.

Metrics, dashboards Designed

PromQL panels, dashboards as typed YAML, JSON Schema and a validator that lists allowed values, apply --dry-run, render preview.

Second provider Designed

Jaeger, Tempo or Loki behind the same four interfaces. The claim above is worth something once the module code does not move to add one.

Alerting Last

Deliberately last. Alertmanager and Grafana alerts already cover this, and a half-built alert engine is worse than none.

Out of scope on purpose: ingest, telemetry storage, anomaly detection, RUM, synthetic monitoring, cost attribution. Tessera reads what your stack already holds, and that boundary is what keeps it small enough to trust.
